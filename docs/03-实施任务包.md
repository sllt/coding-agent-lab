# Coding Agent Lab · 实施任务包

**用途：把产品与技术设计拆成能够单独 Review 的工单。**  
基线：2026-10-04。先读 [产品需求文档](01-产品需求文档.md) 第 1、3、12 章，再读 [技术设计文档](02-技术设计文档.md) 第 2—7 章。本文不是要一次完成所有版本。

## 1. 执行规则

先确定契约与负例，再写实现。一个工单只有一个负责人；同一时刻不要让多个 Agent 随意修改 schema、状态机、公共 DTO 或数据库迁移。并行适合发生在边界固定之后，如独立适配器、页面、已确定契约的测试。

工程判断不能由模型修改测试口径来绕过。出现文档冲突时记录 ADR/问题，不自行放宽安全限制，也不为了通过 CI 删除检查。实现者可以补测试，但不能单方面更改已批准的验收预期。

建议主控负责跨模块 Review 和合并，执行 Agent 负责有限改动；独立 Reviewer 检查事实与负例。这里没有根据特定模型名称预设能力排行，分工应按实际结果调整。

## 2. v0.0：先验证四个真实前提

| 工单 | 产物 | 验收 |
|---|---|---|
| B00 · Pi 版本验证 | 固定依赖版本、最小服务、构建记录 | 当前提交可构建；HTTPHandler、资源 Start/Stop、SSE 不依赖虚构 API |
| B01 · 存储验证 | SQLite 临时库、迁移与事务测试 | PRAGMA 每连接生效；短事务/CAS；关闭后能恢复已确认状态 |
| B02 · 账号与 CLI 验证 | doctor 报告、脱敏真实事件 fixture | 用户授权的小任务确实改文件；知道走哪条授权/计费路径；模型 ID 可用 |
| B03 · 执行环境验证 | 假 CLI、取消与清理测试 | 子进程会派生孙进程；取消/父进程崩溃均可清理或明确 quarantine |

B02 只选择当前最容易合法跑通的一个入口，不强制先 Cursor。没有用户允许时只做静态探测，不使用真实模型调用来试错。

**进入 v0.1 的条件：B00—B03 有实际记录。** 若某个平台失败，缩小兼容范围；不阻塞于同时认证所有操作系统和工具。

## 3. v0.1：单次可信闭环

### M01 · 领域契约与状态机

范围：`internal/domain`、契约测试、必要 ADR。定义 TaskVersion、ProfileVersion、Experiment、Trial、Attempt、Verdict、CleanupState；实现纯函数状态转换与比较指纹。

必须测试非法转换、取消与终结竞争、旧 Attempt 回报、已发布版本不可变。暂不写数据库和 CLI。完成后将字段冻结为 DTO/schema，后续 Agent 不随意改名。

### M02 · SQLite Store 与幂等提交

依赖 M01。实现 schema/migrations、Task/Profile 版本保存、单 Trial Experiment、幂等提交和容量占用事务。只支持 SQLite，不预先做多数据库抽象工厂。

必须测试相同请求重复提交只出现一组 Trial、同 key 不同 body 冲突、终态和取消的 CAS、失败事务无半个计划。写数据库的唯一进程是控制面。

### M03 · Runner 协议与假 Agent

依赖 M01。实现同一可执行文件的 Runner 子命令、受限私有 IPC、按 Attempt 的事件序号和能力凭证、stdout/stderr 独立捕获、超时和取消。

假 Agent 应可模拟成功、失败、挂起、派生子进程、重复终结、超大输出、伪造平台事件。不得让假 Agent 的 `{"type":"Finished"}` 直接控制任务状态。使用假 Agent 完成恢复测试后再接真实账号。

### M04 · 独立工作区与改动包

实现授权源的固定基线、独立副本、文件清单、收集/应用改动包与 diff 导出。首版明确处理普通文件、二进制和删除，拒绝不支持的 symlink/submodule，而不是留下不确定行为。

必须测试未跟踪新文件、修改 `.git/index`、路径穿越、超大文件、隐藏材料和源仓库不被修改。输出摘要应在干净基线重建后可再次验证。

### M05 · 一种执行环境 + 一种真实 Adapter

依赖 B02/B03/M03/M04。优先认证 Docker 路径，只接一个真实 CLI。建立净化的环境、明确的认证引用、固定版本 argv、事件解析与实际模型记录。

未经用户批准不使用自动放开权限的参数。尚不支持的网络限制写成不支持，不能只加一个 enum 就显示“已沙箱化”。出现输出解析变化保留原始记录，不默认成功。

### M06 · Verifier 与任务校准

依赖 M04/M05。实现基线预检、独立候选环境、build/regression/acceptance/policy 检查、数量/ID 约束和证据文件。先用两个维护过的示范任务证明正确补丁通过、错误/空补丁失败。

测试脚本异常与候选测试失败分开；隐藏材料仅在验证端出现；记录 inprocess/blackbox 可信度。不能以 Agent stdout 的测试摘要为权威结果。

### M07 · 生命周期整合和恢复

依赖 M02—M06。将固定 scheduler/supervisor 循环接入 Pi；启动/关闭职责唯一；单 Trial 默认无自动重跑。实现 journal 恢复、身份核对、quarantine 和账号容量释放条件。

重点测试：取消返回 202 后并非立即 clean；旧 fence 不覆盖新结果；控制面重启不重复发起付费任务；单次模型失败不关闭整个 Pi 应用。

### M08 · API、安全和实时数据

在 M01 契约基础上实现技术文档第 14 章的首版 API 子集，加入登录、资源授权、Host/Origin/CSRF、幂等请求、分页、SSE 重放和错误映射。

允许并行于部分 Runner 开发，但只能使用固定 DTO 和假数据 fixture。不要先把“任意 shell 命令执行接口”暴露出来再补认证。

### M09 · 最小 Web 交互

依赖 M08 契约。只做 Setup/配置检查、项目任务、单次提交、运行详情、差异/检查/日志与导出入口。不做排行榜、无限画布、终端 IDE 或模型聊天窗口。

页面展示真实 execution/verdict/cleanup 三组状态。unknown 金额显示未知；无结果显示空状态，不填演示分数。演示截图必须带 demo 标记。

### M10 · 使用量、制品与发布回归

补齐 nullable usage、累计去重、时间分解、日志上限、制品 manifest、维护模式备份与导出。运行技术文档的 v0.1 测试集，生成平台/CLI/认证模式兼容矩阵。

交付条件不是“单元测试全绿”，而是有一次真实 CLI 的执行—独立验收—取消/恢复—导出完整记录。用量不可得可以发布，但必须显示未知；清理不可控或误报 pass 不可发布。

## 4. v0.2：可并行但不同时改核心协议

在 v0.1 稳定后，可并行安排三个工作包：补齐剩余两个适配器；实现有界全局并发与账号容量；实现矩阵与基础对比页面。适配器共享固定 contract，但各自拥有真实脱敏 fixture。

矩阵展开、容量、重试和 usage 的集成最终由主控统一 Review。至少用两个真实项目检查结果可解释性；缺少数据不生成模型强弱结论。

## 5. v0.3 以后的工单

v0.3：受控模型模式、可比性判定、重复实验、按任务配对/聚合、统计方法版本化、flaky 校准。

v0.4：人工 Review、可选盲评、一次修复的独立 protocol。先能解释单阶段结果，再做多阶段。

v0.5：Harbor 子集、外部签名触发/通知。ACP/ATIF/Herdr 分别立项，不与产品核心捆绑同时交付。

v1.0：安装升级、备份恢复、兼容矩阵和安全回归。不要为了“1.0 像大产品”临时塞入组织权限、计费、插件商店或公共榜单。

## 6. 工单提交模板

```text
目标：
  完成一个明确用例，不承担整个版本。

允许修改范围：
  列出 package / 文件；核心 schema 变更必须先提出。

输入与输出合同：
  引用固定 DTO、状态表、API 或协议版本。

必须保持的不变量：
  例如：旧 Attempt 不覆盖新结果；未知费用不变成零。

必须验证的正例与负例：
  至少一个成功场景、一个失败场景和一个边界场景。

交付：
  代码、测试、执行命令及结果、未验证项、迁移/兼容影响。

禁止事项：
  不改变验收要求以迎合实现；不自动调用真实付费 API；
  不自动推送/合并/部署；不以日志文字作为平台控制事件。
```

## 7. 给主开发 Agent 的启动提示词

```text
你要实现 Coding Agent Lab。先阅读 01-产品需求文档.md、02-技术设计文档.md
与 03-实施任务包.md，严格区分产品路线和当前工单。

当前先做 v0.0 中 B00、B01 的最小验证；B02 涉及付费调用必须经用户许可。
后端采用 Go 与 sllt/pi，Pi 锁定到设计文档说明的已查阅提交或经验证的对应版本。
不要改写 Pi 框架，不要创建 Rust 服务，不要自研 Agent，不引入 Redis 或通用工作流。

先核对实际框架 API 和已有仓库结构，列出本次改动与验收项，然后实现。
状态、协议、预算和权限相关未知点必须显式报告，不编造框架方法或模型 ID。
每个阶段提交可 Review 的小改动并附实际测试结果；没有执行的测试写未执行。
不要一次性生成整个平台，也不要为了通过测试降低验收标准。
```

若工程已有代码，先检查当前实现再接续；不要用本提示词把已经完成的版本覆盖重建。
