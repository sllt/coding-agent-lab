## 1. 总体技术决策

采用 **Go + sllt/pi 的控制面、同一 Go 可执行文件中的 Runner 子命令、React + TypeScript Web 前端、SQLite + 本地制品存储**。控制面采用模块化单体；执行工作放入独立子进程和明确的执行环境，而不是塞进 HTTP Handler。

首版只构造一个“定义任务—授权执行—收集改动—独立验收—保留证据”的闭环。真正需要人工重点 Review 的核心是状态转换、进程生命周期、验证边界与用量口径，不是把所有业务改成复杂并发框架。

主要决定如下。

| 项目 | 决定 | 不采用的首版方案 |
|---|---|---|
| 服务框架 | Pi；只在 transport/bootstrap 等边界引用 | 同时维护 Go 与 Rust 控制面 |
| Runner | Go 子进程；每个活跃 Attempt 一个受监督进程 | 自研 Agent 推理循环、把 CLI 塞入请求协程 |
| 调度 | 单服务、持久化计划、有界并发、账号容量控制 | Redis 队列、通用 DAG、分布式租约系统 |
| 数据库 | 本地 SQLite，明确事务与 WAL 策略 | 首版同时兼容 PostgreSQL/MySQL |
| 制品 | 本地不可变文件、摘要、有限保留 | 首版引入 S3 集群、搜索集群 |
| 浏览器实时数据 | REST + SSE，运行控制走显式 API | 首版提供远程任意 Shell WebSocket |
| Agent 扩展 | 固定编译适配器 + 版本化契约 | 动态 Go plugin、WASM 插件平台 |
| 验收 | 基线校准、独立重建、可信控制的检查项 | 读取 Agent 的“成功”文本直接判定 |
| 统计 | 先原始证据与计数，再任务层比较 | 预设“综合能力 92 分” |
