Coding Agent Lab · 产品需求文档

文档版本：1.0 · 设计基线：2026-10-04 · 产品暂名：Coding Agent Lab / agentlab
定位：面向个人开发者与小团队的、自托管 Coding Agent 实验与验收工作台。
配套文档：技术设计文档 · 实施任务包

本文定义建议实现的产品，不表示软件已经实现。版本号 v0.x 指产品路线，而非本文版本。上一次讨论中的模型分数、工时和“AI 可完成比例”只是概念示意，不是本产品的实测数据，也不作为立项依据。

1. 产品决策摘要

做一个让你能够把同一真实开发任务交给不同 Agent 配置，在独立工作区执行，并用可信的验收证据决定哪个结果值得采用的 Web 工作台。

它首先回答四个问题：这次是否真正做成；失败在哪一层；用了多少时间、人工介入和可观测额度；在相似任务上哪种配置更值得再次使用。它不从一开始回答“世界上哪个模型最强”。

技术方向：Go + sllt/pi，Runner 同样先用 Go；React + TypeScript 前端；SQLite 元数据与本地制品目录。 首版一个控制服务、一个本机执行器，不引入消息中间件、分布式工作流或另一个 Agent 推理循环。选型证据与约束见技术文档第 2 章。

交付顺序：先证明账号和执行链路可用，再做单次闭环，再做多 Agent 对比，最后才做统计与工作流实验。 不应先花大量额度建设漂亮排行榜。

2. 为什么值得做，以及什么情况不值得做

2.1 实际问题

你已经拥有多种编码工具和额度，但目前判断容易依赖最近一次印象：某次页面写得好，不代表它在修改已有系统时更可靠；一次编译通过，也不能说明权限、异常处理和回归测试都正确。另一方面，手工复制仓库、传递任务、保存日志、运行测试和对比补丁，会吞掉本应节省的精力。

因此，产品价值不是“多开几个终端”，而是把任务定义、执行条件、实际改动和验收结果关联起来，并保留下次可以复核的证据。

2.2 成功与失败标准

成功的表现是：你确实会在真实项目中反复使用它，能够找回某次实验的完整上下文，能区分 Agent 不会做与平台没跑起来，并减少手工组织实验、反复问模型“你真的测试了吗”的时间。

以下情况应停止扩张范围，而不是继续补花哨功能：现有套餐在合法调用方式下无法进入自动化链路；制作验收任务的人工成本长期超过收益；只能产出主观评分、没有可用补丁与测试证据；为了维护几十个适配器而无法稳定支持自己正在使用的三个入口。

这里没有预设商业收入或开发效率提升百分比。先验证个人工作台的实际价值，再判断是否做商业产品。

3. 用户、场景与产品边界

3.1 首要用户

第一用户是产品作者自己：拥有若干真实代码仓库，能定义验收条件，会使用 CLI，希望比较工具组合并保存有效产出。v1.0 仍允许是一个优秀的单用户产品，不以多租户 SaaS 为目标。

后续用户可以是小团队的技术负责人，但团队成员、组织权限、计费、共享账号和公共榜单均不构成首版需求。

3.2 三类实验，不能混为一谈

实验类型 比较对象 保持不变的主要条件 可以得出的结论 首次版本
Agent 配置对比 CLI、模型、规则、工具和权限组成的配置 任务、基线、验收协议与资源预算 哪套工具配置更适合这些任务 v0.2
受控模型对比 同一开放 Agent 内的不同模型 Agent 版本、工具、提示词、可控参数、环境 在这一固定运行方式下的模型差异 v0.3
工作流对比 单次实现、实现后 Review、Review 后修复 任务与总预算，明确各阶段差异 某个流程是否值得增加成本 v0.4

原生 Agent 中不可见的系统提示词、服务端路由和模型别名可能无法冻结。平台应记录“可控部分的快照”和“不可观测部分”，不能称为严格的纯模型实验。

手工在 IDE 中完成再导入的结果属于 manual/imported，保留其价值，但不与无人干预的自动执行默认合榜。中途指导、修改文件、追加任务都必须形成干预事件，不能事后伪装成首轮独立完成。

3.3 明确不做

首版不做 Agent 推理引擎、模型 API 中转站、IDE、通用 DAG 编辑器、自动模型路由、自主无限重试、多人共享订阅、自动合并代码、生产部署或不可信公共代码的托管执行平台。

Herdr、OMP 或其他会话工具可以继续独立使用。Lab 管理的是实验与验收事实，不接管所有日常终端会话，也不要求把既有工作流全部迁进来。

4. 核心概念与命名

概念 产品含义 关键规则
Project 一个被授权使用的代码项目 保存来源和工作区策略，不等于修改原仓库
Task 一个可持续编辑的任务 是任务目录中的逻辑身份
TaskVersion 已发布的任务版本 提示词、基线、验收、预算冻结后不可变
AgentProfileVersion 一套可执行 Agent 配置的版本 CLI、模型请求值、实际报告值、规则和权限均有来源
EnvironmentVersion 工具链与运行环境版本 镜像、平台、依赖锁、网络策略与缓存策略可追踪
Experiment 一次已冻结的实验计划 TaskVersion × ProfileVersion × 重复次数
Trial 一个计划中的评测样本 例如任务 A、配置 B、第 2 次独立运行
Attempt Trial 的一次物理执行 基础设施恢复产生新 Attempt；不是“偷偷再试一次”
Evidence 验收与过程证据 改动、测试、日志、环境、使用量与人工记录
Verdict 验收结论 pass / fail / inconclusive / unverified

Trial 与 Attempt 分开，是为了避免把“第 3 次才成功”显示成“一次成功”。运行状态、验收结论和清理状态也必须分开：任务功能通过，不等于后台进程已经清理完毕。

5. 从打开产品到取得结果

5.1 第一次使用

用户启动本机服务，创建管理员身份，进入 Setup。选择已经安装并合法认证的 Agent；平台执行 doctor 检查可执行文件、版本、账号状态、指定模型、可写工作区、结构化输出、取消能力与环境隔离。

接下来用一个可丢弃的小任务验证实际链路：创建文件、运行明确的测试、保存补丁、清理进程。用户检查该调用究竟走原有订阅还是单独 API 计费，再确认允许后续执行。doctor 本身不会绕过登录或获取隐藏额度。

只有通过这一步的 Profile 才可以加入自动实验。没有支持的认证方式时，应显示“当前执行环境不可用”，不能暗中切换到付费 API，也不能要求用户把整个个人主目录挂载给 Agent。

5.2 完整的一次任务

导入一个项目，选择基线，编写任务和公开验收要求；准备由用户控制的验证脚本。平台先检查基线是否满足该任务类型的预期：原有回归测试通过，而针对缺失功能的新测试按预期失败。

用户发布 TaskVersion，选择一个已验证 Profile，确认预算并执行。执行器使用独立代码副本，原仓库不被修改。界面展示阶段、原始事件、运行耗时与权限提示。Agent 退出后，平台收集真实工作树改动，在新的验证环境中重新运行验收。

最后展示“哪些必须项通过、哪些失败、是否缺证据”，并提供补丁和报告。采纳补丁是用户的明确操作；Lab 不自动推送、创建带执行副作用的 PR 流程或合并主分支。

5.3 对比同一任务

用户选择两个或三个 Profile，看到预估运行次数与预算上限，再提交 Experiment。所有 Trial 从同一个任务快照开始；不继承另一个 Agent 的上下文、修复补丁或隐藏测试反馈。

比较页面按验收结论、耗时分解、费用可观测性和人工介入显示。点击任何数字都能回到对应证据。用户可以仅采纳一个结果，不需要给所有模型打统一总分。

5.4 额度不足、取消和断线

遇到认证失效或额度不足时，暂停对应账号的后续调度；其他账号可继续。已执行的部分保留，不记为模型不会编程。用户主动取消后，界面先显示“正在停止”，直到执行器确认进程树已结束；取消不意味着已经发生的服务端计费会撤销。

关闭网页不会取消任务。控制服务重启后先核对现有执行器，不能发现心跳丢失就立即再启动一份付费调用。

6.1 第一批必须真正支持的 Agent

Cursor 官方 CLI、Grok Build 官方 CLI，以及一个开放 Agent 入口 OpenCode。DeepSeek 作为 OpenCode 的模型配置，而不是另做一个“DeepSeek Agent”。这能保持第一批只有三套适配器。

官方文档提供了这些工具的非交互入口：Cursor 的输出格式是 stream-json，Grok Build 是 streaming-json，OpenCode 非交互运行可输出 JSON 事件。它们不是同一个协议，必须分别适配。[W1][W3][W5]

“DeepSeek V4.1 Flash”在本文中是用户使用的显示名称。最终 API model ID、账号可用性、推理参数与计费方式必须由本地配置和真实小调用确认，本文不编造对应 ID。

6.2 订阅与 API 的产品表达

Profile 的授权来源至少区分 official_login、api_key、manual_import；计费来源区分 subscription、metered_api、unknown。两者是不同字段。

Cursor 文档支持官方登录与脚本认证；Grok 文档也描述本地认证和 API key 路径。这说明存在接入方式，不证明某个具体套餐在每个模型、模式和环境中都可共享额度。[W2][W4]

因此 Settings 要显示“该路径的权益已由用户确认于何时”，而不是显示未经验证的“剩余 80%”。无官方可用量接口时，只记录本平台可观测调用、用户手工备注和限流事件。不抓取私有账单接口，不绕过限制，不共享他人账号。

7. 任务系统：让复杂度落在可验证的地方

7.1 任务类型

类型 例子 验收重点
修复既有缺陷 某个边界输入使分页重复 复现测试 fail→pass，旧用例 pass→pass
增量功能 给现有页面和 API 增加过滤能力 接口行为、权限、数据一致性与 UI 链路
有约束重构 拆分模块但保留兼容行为 行为回归、公开接口、依赖方向
全栈交付 在现有应用补一个完整管理功能 API、数据库迁移、页面、端到端流程
诊断与修补 根据日志定位资源泄露 可复现症状、修复验证、解释与证据一致

这不是要求所有类型在 v0.1 都有内置模板。首版只需一个通用任务格式和两种示范任务：缺陷修复、增量功能。

7.2 好任务的内容

任务需要公开说明输入、预期行为、限制和交付范围；隐藏的是具体测试实现，而不是偷偷增加没有告知的业务要求。对“更优雅”“像某产品一样好看”等需求，应给可讨论的 rubric 或示例，不把主观审美伪装为自动验收。

对已有项目，必须冻结一个确实可运行的基线。任务的参考解或已合并修复不能存在于 Agent 可访问的未来提交、solution 文件夹或缓存里。尚未形成独立验收的任务只能标记为 exploratory，不能进入硬通过率统计。

7.3 首批任务集建议

先从你实际愿意采纳的工作中挑 6—10 个任务，分布在至少两个项目；这是建设规模建议，不是统计样本量承诺。可以来自 Go 服务、Rust 服务、Web 页面，避免全是“从零写一个漂亮 Todo”。

首次每个任务只跑一个 Profile，先验证验收器本身。验证稳定后，再扩为三个 Profile；重复实验安排在 v0.3。不要一开始跑 100 个未经审核的自动生成任务。

模型可以协助编写测试，但用户要批准验收规则。至少保留基线失败、已知正确补丁通过、明显错误补丁失败这三类校准材料。参考补丁保存在验证端，绝不发送给做题 Agent。

8. 验收、统计与解释方式

8.1 首版只信硬门槛与证据

pass 表示所有已定义的必须验收项通过且证据完整，不表示证明了程序所有性质。fail 表示执行已经提供足以判断任务未达标的证据；inconclusive 表示基础设施、认证、配额或缺失证据阻止判断；unverified 用于尚未验收或仅导入结果。

编译失败、约束内未完成、确定的业务测试失败可以判 fail；镜像拉取失败、账号登录失效不能判模型能力失败。Agent 声称“全部测试通过”只能作为原始文本，不能改变 Verdict。

8.2 比较页默认指标

优先展示通过/失败/未判定的原始计数、任务数、重复数、人工介入、端到端时间和 Agent 执行时间。费用有完整数据时才比较金额；套餐调用可展示耗用事件、可得 token 与用户成本备注，但不把它们强制换算为 API 美元。

不默认提供 0—100 综合分、按代码行数奖励、基于不同测试总数的横向“测试通过率冠军”，或忽略基础设施失败的单一排行榜。必须同时展示可评判样本通过率和整个计划的交付情况，防止通过排除失败样本美化结果。

8.3 重复实验和结论强度

一次成功不能代表稳定性。同一任务的重复运行需要全新工作区和会话，并记录可控参数。不同任务的难度差异很大，重复十次同一个任务也不等于做了十个独立任务。

v0.3 支持按任务聚合后比较、配对分析和任务层面的重采样区间。任务数量少、环境不一致、未知模型路由或大量缺失时，显示“观察性结果”，不自动宣布谁更强。详细口径见技术设计第 13 章。

8.4 Review 的地位

先确定性验收，后主观 Review。Review 可以讨论可读性、维护成本、潜在缺陷，但不能把测试失败覆盖为通过。盲评隐藏模型名称；同一 rubric、相同上下文预算；证据不足就返回不足，不要求模型总能给出数值。

实现 Agent 自审可以作为一个工作流变量；独立 Reviewer 也只是另一个可比较策略。产品不先验宣称谁更好，而是保留对照组和额外成本。

10. 隔离、权限和隐私的产品承诺

默认推荐在专用 Docker 执行环境运行，仅处理本人授权的项目；原仓库、控制数据库、Docker socket、SSH agent、全局登录目录、其他项目和隐藏验证材料都不进入 Agent 工作区。容器能够减少暴露面，但不是运行任意恶意公共代码的绝对安全边界。[W7]

对现有官方 CLI 的认证或平台兼容性不满足容器场景时，可以显式启用 native-trusted 兼容模式，建议使用独立操作系统用户。界面必须写明“本机进程执行，不提供容器级隔离”，它不能作为 silent fallback，也不能与容器结果默认合榜。Git worktree 本身不是安全隔离。[W6]

向第三方 Agent 发送代码意味着相应供应商可能接收到仓库内容。导入私有仓库时需确认授权，默认不暴露部署密钥和生产数据。Agent 在拥有工具执行能力时仍可能接触同执行环境内的认证材料；仅放入环境变量不等于密钥对它不可见。

本产品不宣称能够让 Agent “看不到自己用来调用模型的所有凭据”。需要更强保护的团队场景，应另行设计凭据代理、网络隔离与组织级授权，不把它当作首版已有能力。

12. 版本路线与进入下一阶段的条件

v0.0 · 可行性验证，不做大界面

验证 Pi 的最小服务、SQLite 事务、一个 Runner 子进程和一个真实 CLI。完成认证路径与模型可用性检查、输出解析、真实文件写入、超时取消、无孤儿进程、用量来源确认。保留原始小样本作为适配器 fixture。

退出门槛：一个已授权入口确实可以完成可丢弃任务并被停止。 不能只写“理论上支持”。如果第一个 CLI 不满足条件，选择另一个已验证入口，不绕过认证、不暗中转计费路径。

v0.1 · 一个可信的执行—验收闭环

包含项目/任务版本、单 Profile、单 Runner、独立工作区、基线预检、单次执行、取消恢复、差异与检查结果、制品导出和基础认证。使用 Docker 路径作为主要验收路径；本机兼容执行仅在安全边界已明确、测试通过后启用。

退出门槛：正确补丁通过、错误补丁失败、平台故障未判定；重启与取消不产生重复执行或孤儿进程。 不要求统计图、Reviewer、自动路由或多租户。

v0.2 · 三个入口与日常对比

加入 Cursor、Grok Build、OpenCode 的通过测试配置、账号级串行与全局有界并发、任务矩阵、对比表和预算检查。适配器与 CLI 版本有兼容矩阵。使用至少两个真实项目的任务进行日常验证。

退出门槛：不同工具的失败原因、未知费用和人工介入能够清晰区分。 这是第一版适合你持续使用的产品形态。

v0.3 · 可信重复实验

加入同 Agent 换模型模式、重复数、配对与任务层聚合、可比性提示、基线与验收器校准，记录 CLI/规则/实际模型信息漂移。优先解决“结论是否可信”，而不是丰富图表种类。

v0.4 · Review 与有界流程实验

先做人工 Review，再做可选模型盲评；实现→Review→一次修复是新的 protocol。保存前后补丁和阶段成本，不能覆盖原始 single-pass Trial。依然不自动合并。

v0.5 · 互操作

以需求驱动加入 Harbor 格式子集或其执行器桥接、外部 API 触发、签名结果通知。ACP、ATIF、Herdr 联动各自独立评估，不因为协议存在就同时实现所有协议。[W8]

v1.0 · 稳定的个人工作台

完成安装升级、备份恢复、磁盘配额、兼容矩阵、安全回归、取消重启压力测试和文档。没有多租户、计费、公共榜单，也可以发布 1.0。模型推荐先作为有证据的建议，自动分配必须另立范围。

13. 产品验收与停止线

最终验收不是“页面都能点”，而是以下端到端场景：真实 Agent 改对任务；故意错误和空测试无法获得通过；伪造成功日志不改变验收；凭据失效停止对应账号；控制服务重启不会重复付费启动；取消杀掉进程树；新旧实验快照不互相污染；未知金额不显示零；源仓库没有被写入；报告丢失证据时明确降级。

首版不能妥协的三件事是：不误报通过、不失控执行、不隐瞒不可观测性。 页面美化、多模型覆盖率和复杂统计都应排在这三件事之后。

1. 总体技术决策

采用 Go + sllt/pi 的控制面、同一 Go 可执行文件中的 Runner 子命令、React + TypeScript Web 前端、SQLite + 本地制品存储。控制面采用模块化单体；执行工作放入独立子进程和明确的执行环境，而不是塞进 HTTP Handler。

首版只构造一个“定义任务—授权执行—收集改动—独立验收—保留证据”的闭环。真正需要人工重点 Review 的核心是状态转换、进程生命周期、验证边界与用量口径，不是把所有业务改成复杂并发框架。

主要决定如下。

项目 决定 不采用的首版方案
服务框架 Pi；只在 transport/bootstrap 等边界引用 同时维护 Go 与 Rust 控制面
Runner Go 子进程；每个活跃 Attempt 一个受监督进程 自研 Agent 推理循环、把 CLI 塞入请求协程
调度 单服务、持久化计划、有界并发、账号容量控制 Redis 队列、通用 DAG、分布式租约系统
数据库 本地 SQLite，明确事务与 WAL 策略 首版同时兼容 PostgreSQL/MySQL
制品 本地不可变文件、摘要、有限保留 首版引入 S3 集群、搜索集群
浏览器实时数据 REST + SSE，运行控制走显式 API 首版提供远程任意 Shell WebSocket
Agent 扩展 固定编译适配器 + 版本化契约 动态 Go plugin、WASM 插件平台
验收 基线校准、独立重建、可信控制的检查项 读取 Agent 的“成功”文本直接判定
统计 先原始证据与计数，再任务层比较 预设“综合能力 92 分”

2.2 Pi 已有能力与适配方式

pkg/pi/build.go 的 Build 使用显式配置与资源声明，区分 Owned/Borrowed；资源可按顺序启动、反向关闭。它适合将 SQLite、HTTP 服务和调度监督器的启动关闭放到一处管理。[R3]

pkg/pi/lifecycle.go 的 app.Go(name, fn) 是应用级长生命周期 Worker：必须在应用启动前注册；普通错误会触发应用关闭。它不是持久化作业队列，也不是每次 Trial 的提交接口。[R4]

因此，Lab 只在启动时注册固定的 scheduler/reconciler 等循环。某次 Agent 返回非零、测试失败或账号限流，应持久化为运行结果并继续服务，不能向 Pi 的应用 Worker 冒泡为 fatal error。注册成功也不能被当成任务已持久化。

README 描述了 HTTPHandler()、显式 HTTP status、response.Stream、身份与业务授权边界。它们与 API 和 SSE 的需求相符，但本文没有读取 stream 全部实现，所以长连接 flush、取消和中间件超时必须在 v0.0 做集成验证。[R5]

build_test.go 中已有配置隔离、SQLite 启动、资源回滚、并发生命周期等测试用例。这是代码中可见的测试覆盖，不是本次已经运行通过的证明。[R6]

2.3 Pipi 的真实优点和剩余工作

Pipi 不是“只能写简单 Rust Web”的框架。当前 Cargo.toml 使用 Axum、Tokio、SeaORM/SQLx，并具有认证、存储、缓存和多种后台队列能力；AppContext、Hooks、Initializer 可以扩展路由、共享服务与关闭逻辑。[R7][R8]

但现有后台队列不等于 Lab 运行引擎。在已读的 src/bgworker/mod.rs 范围中，未配置 provider 的 Queue::None 分支可以返回 Ok(())；Lab 启动必须对此 fail-closed，不能将“没有可用执行器”表达为成功入队。[R9]

在 src/bgworker/sqlt.rs 已读的 worker 循环中，取消检查位于循环入口及空闲等待，正在执行的 handler(...).await 没有由该层主动与取消令牌竞速。具体 handler 可以自行协作取消，但长时间 CLI、进程树终止与强制回收仍要由产品实现，不能仅依赖队列 CancellationToken。[R10]

Pipi 默认同时启用多个后台队列 feature，Pi 的 go.mod 也包含较多数据源和观测依赖。两者都应测量实际依赖和产物，不可简单声称“Go/Pi 天然更轻”。Pipi 声明的 MSRV 也需要与真实锁文件共同验证，而不是仅凭声明作保证。[R7][R11]

结论是项目优先级判断，而不是 Rust 能力判断。 假如目标改为“用一个真实产品推动 Pipi”，Rust 方案仍然成立；但应把 Pipi 的生命周期、后台任务和 feature 验证单列里程碑，不能让 Lab 同时承担框架重构。当前建议直接选 Pi，未来只在测量出独立热点时考虑局部改写。

2.5 与 Pi 的具体边界

internal/domain、internal/app、internal/runner 不依赖 *pi.Context。业务方法接受标准 context.Context 和明确参数。Pi 负责 transport 适配、已验证身份的接入与应用资源生命周期，不承载 Task/Trial/Sandbox 业务概念。

SQLite 的首版实现选择由 Lab 的 store/sqlite 持有一个 *sql.DB，通过 Pi 的 WithResource 显式管理启动、迁移、关闭，不同时启用 WithManagedSQL。原因是 WAL、单写者、备份与崩溃恢复是产品必须看得见的存储契约；不是 Pi SQL 不可用。以后改为 Pi SQL 句柄时，只替换存储边界并确保唯一关闭责任。

HTTP 采用 app.HTTPHandler() 接入宿主 http.Server，由宿主组合 API 与嵌入式静态文件；Pi 自带 HTTP/gRPC listener 关闭，避免双重监听。所有路由在获取 Handler 前注册，HTTP Server 的生命周期仍通过显式资源监督。实际代码需使用已核对 API，不能让模型臆造 app.RunJob、app.Sandbox 或未经核实的静态文件辅助方法。

依赖先锁定上述提交所对应的可解析 module 版本，实施时通过 Go 工具确认可用 tag/pseudo-version；不使用 @latest，不在文档中伪造未验证的 pseudo-version。

“同一个程序包”不意味着“所有逻辑同一进程执行”。Runner 子命令不启动 Pi Web 服务，不直接访问控制数据库；它负责执行机械动作、发送事件和保存本次运行的受控日志。最终验收归类和实验状态仍由控制进程按照可信规则决定。

每个活跃 Attempt 使用独立 Runner。v0.1 只有一个活跃 Attempt，v0.2 才启用有界并发。此时不设计远程 Runner 注册中心、动态伸缩或多控制节点。

4. 领域模型、不可变版本与可比性

4.1 版本图

Project ── Task ── TaskVersion ───┐
AgentProfile ── ProfileVersion ──┼─ Experiment snapshot
EnvironmentVersion ─────────────┤         │
ProtocolVersion ────────────────┘         └─ Trial × N ── Attempt × M
                                                          │
                                                     Evidence / Checks

v0.1 的 Experiment 可以只有一个 Trial，界面可隐藏这个概念；底层仍保留计划快照，避免 v0.2 重写数据模型。未来 Review 是独立实体，不覆盖生成结果。

4.2 必须冻结的内容

TaskVersion 保存完整提示词、项目授权引用、基线 commit/tree 内容摘要、允许修改范围、公开规则、验收配置与摘要、环境版本、预算和任务类型。源码不可因分支移动而变化。

ProfileVersion 保存适配器版本、CLI 路径/版本/可得的二进制摘要、请求模型 ID、参数、规则/技能/插件/MCP/hooks 的受控快照、权限、认证引用和官方设置中不可冻结的说明。凭据本体不进入版本快照。

EnvironmentVersion 保存 OS/architecture、镜像 digest、工具链、锁文件摘要、资源限额、网络模式、缓存策略和认证挂载策略。仅保存镜像 tag 不足以冻结环境。

ProtocolVersion 保存是否允许自主工具调用、总时间、Agent 内重试的可观测性、是否有人介入、反馈范围、是否做 Review/修复。CLI 内部不可见重试也应标为 unknown，而不是假设为零。

4.3 草稿与执行快照

YAML 只用作人类编辑的草稿格式。发布时严格解码、拒绝未知字段和重复键、限制大小/深度，转成字段明确的规范 JSON，填充真实摘要和版本引用后计算 SHA-256。哈希算法与 canonicalization 版本一同保存；金额不用浮点数。

base_ref: master 可以出现在草稿中，但执行快照必须是完整固定提交及源码内容摘要。environment_ref 必须解析到已存在版本；未验证模型名、空 doctor 结果、占位镜像摘要都不能进入执行队列。

4.4 两种指纹，不做错误比较

execution_fingerprint 包含 Task、Profile、Environment、Protocol 等全部版本，标识本次条件。

comparison_key 根据实验类型计算：Agent 配置对比允许 Profile 不同；受控模型对比只允许声明的模型变量不同；其他预算、验收和环境保持一致。不能直接要求不同模型的完整 fingerprint 相同，也不能仅按任务标题归组。

实际模型若由服务端报告为不同 ID，保留任务结果，但标记 model_resolution_mismatch 并暂停默认合榜。云端 alias 可能变化时，报告中显示不可完全复现的限制，不将请求别名当成固定权重版本。

5. Task 与验证协议

5.1 任务配置原则

示例草稿见 examples/task-draft.yaml。任务引用控制面已登记、由用户批准的 verifier，不把任意 curl | bash 当成可信测试。公开要求应给 Agent 足够信息，隐藏验证实现不包含未告知的新业务要求。

通用检查类型保持少量：build、regression、acceptance、policy、manual。required 为真时必须有结果；manual 未完成不能自动 pass。每个检查保存稳定 check ID、阶段限时、最低用例数或预期 case ID、结果解析方式与可信度级别。

5.2 基线预检

对修复/新功能任务，回归项通常要求 baseline=pass，新增目标用例要求 baseline=fail；候选补丁两者都应通过。重构类任务可以全部 baseline=pass，并另外定义接口或结构约束，不强制每个任务都必须有红测试。

Task 发布前预检并校准 verifier。实验执行前，重新检查环境解析和预检缓存有效性；只有 source/environment/verifier 三者摘要一致才可复用基线结果。否则重新预检。

预检失败属于任务或环境配置问题，阻止模型调用。不能先花额度生成，再发现原项目本来就不编译。

5.3 独立验证流程

Agent 停止且其子进程被确认清理后，由可信收集器得到内容清单和改动包。验证端从原始基线重建，再应用允许的改动；不使用 Agent 改过的 git index、构建缓存、测试结果文件或已启动服务作为验收事实。

对 HTTP/UI 场景，优先使用独立 verifier 容器控制黑盒请求，Candidate 容器运行修改后的应用。两者在受限的临时网络内，Candidate 不拥有 verifier 文件系统。Playwright 的浏览器、字体、视口与截图环境固定；图像差异只代表约定快照差异，不自动等于“设计美感”。[W9]

对 Go/Rust 单元测试，需要在候选代码参与执行的环境中编译或加载测试。此时只能承诺隐藏测试在做题阶段不可见，不能保证恶意候选代码无法干扰进程内测试或伪造其框架输出。结果标记 assurance=inprocess；更强黑盒检查标记 assurance=blackbox。read-only 测试挂载可防直接修改，但不防读取，也不等于完整反作弊。

Harbor 已提供独立 verifier 环境选项，说明“重新建环境验收”是可复用的方向；但其默认共享模式、制品传递与 Lab 协议并不自动等价，后续桥接时必须显式映射。[W10]

5.4 判定规则

所有必须检查均有可信来源、满足数量/ID预期、通过且没有 policy 违规，才可以 pass。退出码为 0 但零个用例、只输出“PASS”、删除测试或跳过必须项，不构成通过。

自动检查失败不能由模型 Review 改成通过；对 verifier 的修复必须创建新版本并重新验收，保留旧记录。缺失关键产物、解析器不能识别新版本输出或 verifier 自身崩溃，结论为 inconclusive。

6. 存储模型与事务

6.1 SQLite 策略

SQLite WAL 允许读写并发但仍只有一个写者，且 WAL 要求同主机共享内存协调，不适合放在网络文件系统。[W8] 首版因此采用一个控制进程、短事务、有限连接，所有日志不逐 token 写数据库。

建议配置：foreign_keys=ON；本地 WAL；synchronous=FULL 用于确认后的元数据持久性；适当 busy_timeout；写连接串行化。连接级 PRAGMA 要对每个新连接设置，不能在任意一个连接执行一次就假设全池生效。实际 DSN/驱动选项在 v0.0 实测。

数据库访问以 database/sql 为边界，modernc.org/sqlite 版本与锁定依赖一致；选择此方案是避免首版额外 native SQLite 工具链，不是性能优越承诺。查询明确编写，初期不用 ORM；动态排序字段采用白名单。

6.4 状态与文件的一致性

SQLite 与文件系统没有跨资源原子事务。制品先写临时路径、flush/fsync、在同一文件系统内 rename，再提交元数据引用；需要持久化的目录项按支持平台同步。崩溃可能产生孤儿文件，由恢复扫描处理。

如果数据库引用的文件缺失或摘要不符，标记 evidence_missing 并降级展示，不能仍称完整可复现。日志可采用分段 durability watermark：只有已刷盘并登记的游标算持久化确认；不能声称每个已显示 token 在掉电后都存在。

7. 调度、状态机、取消和恢复

7.1 三组状态

execution_state：queued → preparing → running → collecting → verifying → completed；非终态可进入 cancelling → cancelled；无法继续执行的基础设施问题进入 aborted。

verdict：unverified | pass | fail | inconclusive。

cleanup_state：pending | clean | failed | quarantined。

正常验收完成时 completed + pass/fail；在公开时间预算内确定未完成，可以在进程已终止后 completed + fail + agent_time_limit。认证、额度、执行器崩溃、关键证据缺失等无法评判情况使用 aborted + inconclusive。用户取消使用 cancelled + unverified，并保留已有部分检查，但不纳入完成率分子。

功能已验收的记录可以先 completed，清理仍 pending；账号容量只能在 clean 后释放。清理异常作为显著告警，不能因为评分已经生成就忽略孤儿进程。

7.2 Trial 与 Attempt 的关系

Trial 是计划样本；Attempt 是实际执行。v0.1 禁止自动重跑 Agent，默认 max_auto_infra_retries=0。用户手工重试会创建新的 Attempt 并注明原因，原有结果不被覆盖。真正的独立重复实验创建新的 Trial。

v0.2 若加入基础设施自动恢复，仅允许有充分证据证明尚未进入模型调用阶段的准备失败；不确定是否已经调用过 Provider 时不得自动重启。不允许通过“重试直到成功”美化首轮通过率。

验证器自身的重跑可以复用同一不可变补丁，但检查记录增加 check_run，不能改写以前的失败。改变 verifier 内容仍要生成新版本。

7.3 启动流程

  1. 验证 Task/Profile/Environment、用户授权和账号状态，计算计划与预算。
  2. 在 SQLite 短事务中检查未取消与容量，创建 Attempt、随机能力凭证摘要、递增 fence，将 Trial 置 preparing。
  3. 事务提交后启动 Runner，将 ExecutionSpec 通过私有通道发送，不把权限令牌放入可泄露的命令行。
  4. Runner 创建独立环境，先持久记录“即将允许启动 Agent”，再启动 CLI，并报告事实事件。
  5. CLI 结束后，Runner 确认该阶段进程树停止；收集改动、重建验证环境、运行检查、提交制品清单。
  6. 控制端校验当前 Attempt/fence、证据和状态后提交结果；清理完成后释放容量。

fence 只防止旧执行器把状态写回覆盖新结果，不会撤销已经发给 Provider 的请求，也不能保证外部计费 exactly-once。

7.4 私有 Runner 协议

首版使用继承的私有 pipe 或 Unix socket 的 NDJSON 帧协议，限定最大帧长度和协议版本。Agent stdout/stderr 必须单独捕获，不能直接复用 Runner 的控制 stdout。控制凭证和 IPC fd 不传给 Agent 子进程。

控制消息：Start(ExecutionSpec)、Cancel(reason)、Shutdown。Runner 事件：Ready、PhaseChanged、Heartbeat、LogSegmentCommitted、PatchCollected、CheckObserved、UsageObserved、CleanupCompleted、Finished。

每条事件有 attempt_id、fence、sequence、event_type；控制端按私有通道认证身份，不信任 Agent 文本里的 run_id 或 event_type。重复 sequence 可幂等丢弃，缺号要保留 gap 标记。

Runner 没有修改任意 Trial 的权限。IPC 接收端也不允许通过“执行任意命令”消息扩展能力；它只能执行已经冻结、用户授权的 ExecutionSpec。

7.5 取消与进程树

取消 API 先在事务中写取消意图，再返回 202。Supervisor 检查后发送取消；Runner 先温和终止、等待有限宽限期，再强制终止并 reap。HTTP 连接关闭不触发取消 API。

Go 的 os/exec 不隐式经过 shell，适合使用 argv 启动；但仅使用 exec.CommandContext 不等于完整处理所有后代进程。[W7] Unix native 模式需进程组与退出回收；Docker 模式用已记录容器 ID 停止/kill/remove，并验证不存在。Windows Job Object 不在首批承诺范围。

不能仅依赖父 PID 判断进程身份，避免 PID 复用误杀。使用创建时记录的资源 ID、随机标识和运行元数据；native 无法确认身份时进入人工回收，不根据猜测杀死其他进程。

7.6 控制面重启与失联

本机首版策略是 不透明续跑、不盲目重跑。正常关闭先停止调度，再取消活跃 Runner；控制通道 EOF 时 Runner 尝试停止其管理的所有资源并刷盘。控制面恢复后扫描未终结 Attempt、运行 journal、带受控标签的容器和资源清单。

恢复发现 处理
已持久化最终结果和一致制品 幂等补交元数据；核对清理
Runner 已退出，资源已清理，只有部分结果 aborted/inconclusive；保留部分证据
仍有属于本 Attempt 的容器 先确认身份并停止、回收；不启动替代执行
是否还在执行无法确认 quarantined、冻结容量，等待明确处理
准备占位但有证据证明从未启动 终结该 Attempt；按配置允许重新排队或人工重试
控制数据与文件摘要冲突 隔离记录，不强行修成 pass

首次实现不用“租约到期立刻接管”的分布式方案。心跳失联是调查信号，不是已经停止的证据。故障恢复的不确定费用也要保留为 unknown。

7.7 与 Pi 应用生命周期的结合

Pi 的固定 supervisor loop 可以调用 Scheduler.Run(ctx)，但该循环内部必须区分 TrialFailure 与 ApplicationFatal。前者记录结果并继续；只有数据库永久不可写、核心状态不变量破坏等导致服务无法安全运行的情况，才令应用 Worker 返回错误。网络暂时失败与模型调用失败不应关闭 Web。

资源清理顺序应为：关闭新提交/调度入口 → 取消并回收 Runner → 刷盘日志与结果 → 停止 HTTP/SSE → 关闭数据库。启动时以相反依赖顺序准备。SSE/HTTP 在 draining 阶段只读可见，不能再创建任务。

8. Workspace、Sandbox 与安全边界

8.1 三个文件域

控制域保存 SQLite、认证配置、执行 journal、verifier、参考解和制品索引；Agent 域只包含基线工作树、被批准的公开上下文、临时 HOME 与有限的认证材料；Verifier 域包含独立验收材料和从基线重建的候选代码。

容器挂载必须逐项白名单配置。禁止挂载整个主目录、原项目根、共享可写 .git、控制面数据目录、Docker socket、SSH agent socket 和其他 Agent 的会话。Agent 容器不允许直接访问控制 API 或本机管理网段。

8.2 基线和工作区创建

仓库解析由控制侧完成并校验来源。远程来源默认只接受明确允许的 HTTPS host；本地仓库只能由管理员登记到允许根目录。拒绝任意 file://、scp-like URL、重定向到内网、未批准的子模块和 Git transport helper。网络访问防护同时考虑 DNS 解析与实际连接地址，不能仅做字符串前缀判断。

将固定基线导出为独立文件树；确有 Git 工具需要时，在副本中生成仅含基线的独立仓库。关闭自动 hooks、模板和继承全局 Git 配置，不暴露包含未来修复的历史。v0.1 默认不支持任意 submodule/LFS；需要时单独制作并冻结展开后的输入。

Git worktree 会共享部分仓库元数据，因此不是安全沙箱。[W6] 可以在 native-trusted 自用模式中作为便利选项，但不是严格实验的默认隔离方式。

8.3 改动收集不能只信 git diff

可信收集器对停止后的工作树进行有界遍历，以基线内容清单为参照，记录增加、修改、删除、文件模式和二进制内容。Agent 可以修改自己的 .git/index，因此不能把它返回的 diff 当成唯一真相。

不跟随越界 symlink、不导入设备文件/FIFO/socket；限制路径长度、文件数、单文件大小和总大小，拒绝绝对路径、.. 路径、危险 gitlink 与逃出工作区的硬链接关系。正常符号链接若任务确需使用，应有单独类型校验与平台测试，首版可以明确拒绝。

改动包采用内容清单 + blob，导出的 patch.diff 是方便人类使用的视图。应用改动到干净基线后重新计算内容摘要，确保验证的内容与收集的内容一致。新增且未跟踪的源码不能因为未加入 Git index 而被漏掉。

8.4 Docker 执行策略

使用预先批准并按 digest 锁定的镜像；非 root 用户、只读根文件系统、有限可写工作区/tmp、drop capabilities、no-new-privileges、PID/CPU/内存/磁盘限额，禁止 privileged、host network 和任意宿主 bind mount。

Agent 阶段需要访问模型服务，但验证阶段通常不需要公网。Docker bridge 本身不提供域名 allowlist；仅设置 HTTP_PROXY 也不能阻止代码绕过代理。要声明 network=restricted，必须有可验证的强制出口控制与内网阻断；没有该能力时诚实标记 network=unrestricted，仅允许运行本人可信任务，不用于严格隔离组。

首版可以先验收“无危险宿主挂载 + 验证阶段离线 + 有限资源”的个人场景，再单独完善模型 API 的强制出口路径。不能因为容器启动成功就声称恶意代码无法出网或逃逸。Docker 官方安全文档也强调 daemon 与容器配置的信任边界。[W11]

多个实验不共享可写 npm/cargo/go build 缓存；需要加速时使用准备好的只读依赖缓存或分 Trial 可写层，并记录缓存策略。热缓存与冷缓存的运行时间不能直接混报。

8.5 native-trusted 兼容模式

该模式允许在已授权的本机 CLI 环境下执行，便于复用特定官方登录，但必须显式确认。独立 OS 用户比仅换 HOME 更能减少对本人文件的暴露；平台仍不能承诺它与 Docker 同等安全。

原有 HOME 中的登录、规则、技能、MCP、hook 和历史会话不能全部继承后仍称可控实验。通过 profile 注册需要的最小配置；若工具不支持隔离加载，则记录该限制，实验归到 observational/native 分组。

native 模式无法依靠“独立目录”阻止同 UID 进程读取控制面数据，因此严格多用户或对抗性任务不允许使用。强安全需求应采用专用 VM/机器与单独授权，而非不断给目录加约定。

8.6 凭据的真实保护范围

控制面只保存 credential_ref，解析发生在受信任执行准备侧；浏览器不能取回明文。使用系统凭据存储或权限受限文件。备份与导出默认排除凭据；凭据轮换不修改旧实验的内容摘要，只记录凭据版本引用与时间。

官方登录的 token 刷新和 Keychain 依赖必须在 doctor 中实测。不能为了容器可用而随意复制整套登录目录；只导入工具文档允许、且授权边界清楚的最小材料。

放在同一 Agent 执行环境里的 API key，理论上可能被该 Agent 的工具或候选代码读到。环境变量、只读文件和日志脱敏都不能消除这一点。采用最小权限、专用可撤销凭据和出口约束；更强的凭据代理在后续版本独立设计。

9. Agent Adapter 合约与三个首选入口

9.1 Adapter 做什么、不做什么

Adapter 仅负责能力检测、准备启动参数、解析官方输出和报告工具特有事实。超时、进程回收、权限、文件收集和最终判定由通用 Runner/Verifier 处理。

它不隐藏新的推理循环，不自主无限续聊，不把模型调用失败自动换成另一个 Provider。CLI 自带的自主多步行为属于该 Agent 的能力，需要记录而不是重新实现。

9.2 建议的 Go 接口草案

// Agent Lab 的接口草案；用于固定边界，不是 Pi 的已有 API。
type Adapter interface {
    Name() string
    Probe(ctx context.Context, req ProbeRequest) (Capabilities, error)
    BuildLaunch(ctx context.Context, req LaunchRequest) (LaunchSpec, error)
    NewDecoder() EventDecoder
}

type LaunchSpec struct {
    Executable string
    Args       []string          // 不拼接 shell；不包含凭据
    WorkDir    string
    Env        map[string]string // 净化后的 allowlist
    StdinFile  string            // 仅在 CLI 明确支持时使用
}

type Capabilities struct {
    CLIVersion            string
    SupportsHeadless      bool
    SupportsStructuredLog bool
    ReportsModelID        bool
    ReportsUsage          bool
    SupportsNativeBudget  bool
    SupportsSessionResume bool
    TestedPlatform        string
}

type EventDecoder interface {
    Decode(stream string, frame []byte) ([]ObservedEvent, error)
}

ProbeRequest、LaunchRequest 和 ObservedEvent 由实现时的 DTO/JSON schema 定义，字段遵循本章及第 4、10 章。能力中的 false 和“无法探测”要在结果数据中区分，不能把不支持当成暂时没数据。只有通过执行 fixture 的能力才能标记 verified。

9.3 入口差异

Adapter 文档确认的无交互形式 结构化输出 必须特别验证
Cursor agent -p，写文件需授权 --force --output-format stream-json 实际写入、登录范围、真实模型和流输出完整性
Grok Build grok -p，模型 -m --output-format streaming-json 关闭自动更新、fresh session、审批策略
OpenCode opencode run，模型 provider/model --format json 专用配置、env/.env 继承、事件与用量来源

这些入口来自当前官方文档，但仍需对实际安装版本做 doctor 与 fixture 测试。[W1][W3][W5] 不同格式的枚举值不能复制粘贴为一个统一字符串。

下列启动样式只用于说明 argv 组装，不是可以在个人主目录随意执行的建议：

Cursor:   agent -p --force --output-format stream-json --model MODEL PROMPT
Grok:     grok --no-auto-update -p PROMPT --output-format streaming-json -m MODEL
OpenCode: opencode run --format json --model PROVIDER/MODEL PROMPT

实际工作目录由 Runner 设置。自动批准工具的选项只能在已批准的隔离与权限策略下开启；Grok/OpenCode 需要的批准参数由固定版本适配器验证后加入，不让通用调用层默认附带“允许一切”。长提示词以工具已支持的文件/stdin机制传入，或使用受限长度 argv；未核实支持时不能发明 flag。

9.4 doctor 的内容和报告

doctor 依次检查版本、可执行来源、模型配置、授权来源、环境兼容性、可写临时目录、无交互响应、输出解析、最小文件改动、正常退出、取消、子进程清理、可观测 usage，以及配置隔离。涉及付费的 smoke test 必须先显示并获准，静态检查不自动发起付费请求。

认证状态只能证明可认证，不证明特定模型能调用、额度可共享或费用可控。允许用非敏感小任务做真实调用，并保存 entitlement_verified_by、时间、计费路径和用户确认，不用臆测套餐剩余额度。

Cursor 官方提供登录/认证路径，Grok 提供本地登录与 API key 路径；本文不保证用户某个套餐的具体权益。[W2][W4] 用户叫作 DeepSeek V4.1 Flash 的配置，只有 provider/model 真实解析通过后才可发布。

9.5 版本漂移与解析失败

CLI 版本发生变化时生成新 ProfileVersion 或要求重新 doctor。Grok 文档提供关闭自动更新的选项；其他工具通过固定安装产物/镜像和启动前校验版本控制漂移。[W3]

未知事件类型保留为原始记录，不直接 panic；关键终止事件无法判读时标记 adapter_protocol_error。CLI 的退出状态、真实文件与独立验收都要保留；不能因缺少“漂亮的完成事件”丢弃已得到的补丁，也不能据此伪造成功。

默认新会话，不使用 --continue。即使工具支持 resume，也不在 v0.1 做会话恢复。后续恢复行为属于新的 protocol，并记录是否重新发送了模型请求。

9.6 测试 fixture 的最小集合

每个适配器都应有真实脱敏事件样本：正常、非零退出、限流、认证失败、输出截断、未知字段、重复终止、usage 缺失、usage 累计快照、运行中取消、包含终端转义、超大行。解析器测试独立于实际账号，避免每次 CI 消耗套餐。

10. 事件、SSE、制品与背压

10.1 统一事件，但保留来源

{
  "schema_version": "agentlab.event/v1",
  "attempt_id": "attempt-example",
  "fence": 1,
  "sequence": 17,
  "observed_at": "2026-10-04T09:00:00Z",
  "origin": "agent_observation",
  "type": "message",
  "payload": {"text": "示例输出，不是平台验收结论"}
}

origin 至少区分 control、runner、agent_observation、verifier。只有可信 Runner/Control 消息可以驱动状态。Agent 输出即使包含相同 JSON 字段，也只是嵌套文本，不能被提升为 CleanupCompleted 或 VerifiedPass。

平台分配 attempt_id 和序号，工具的 session ID 另存。时间同时保留 wall-clock 与本进程单调计时推导的阶段 duration；重启前后不能用不同进程的 monotonic 值相减。

10.2 有界存储策略

原始输出与规范事件按段追加到文件，索引和 durable watermark 批量持久化。stdout 和 stderr 同时消费，避免单管道阻塞；Reader 有显式行长/帧长上限，不能默认依赖较小 Scanner 上限而遇长 JSON 崩溃。

默认示例政策可设：单原始帧 1 MiB、内存事件缓冲 8 MiB、每 Attempt 日志 64 MiB、制品 512 MiB、文件数 10,000。它们是可调整的安全起点，不是容量测评结论。超限必须记录截断或 policy failure，不能无限放宽。

慢浏览器只影响自己的订阅：断开并提示通过游标补读；不让慢消费者阻塞 Agent stdout 导致任务挂死。日志存储写满时进入明确的证据异常，停止继续生成以避免无法记录的付费运行。

10.3 SSE 契约

GET /api/v1/attempts/{id}/events 支持 Last-Event-ID；SSE id 采用稳定的 attempt_id:sequence。历史读取先回放已保留事件，再切换实时流。若游标落在已删除区间，返回明确 gap/snapshot_required，不假装无缝恢复。

统一设置 event-stream、禁代理缓冲、按策略 flush、心跳和连接限额。长连接的寿命独立于普通请求超时；Pi/宿主 middleware 不应在写过事件后补 JSON 错误。可使用 Pi 已说明的 stream 机制，或宿主标准 http handler，并以集成测试确定实际行为。[R5]

v0.1 不做双向终端。取消使用 REST，人工补充指令暂不开放；后续加入时必记 intervention 并改变实验协议。

10.4 制品类型和导出

制品包括：输入快照、环境与 CLI 版本、公开任务、脱敏事件、内容清单、diff/改动 blob、检查结果、错误日志、截图/trace、usage 来源和清理记录。隐藏 verifier 与参考解不默认打包给普通结果读取者；管理员也应显式选择是否导出。

导出包中的 manifest.json 记录 schema version、文件摘要、证据缺失/脱敏/截断标记和创建工具版本。报告与制品相互引用，能够解释结果而不依赖在线界面。无法再次访问模型权重并不影响证据审查，但要区分“结果可审计”和“模型执行可精确重现”。

HTML、SVG、终端日志和 trace 均按不可信制品处理。默认下载或以严格沙箱展示，不在控制台同源且允许脚本的 iframe 中直接打开。敏感内容脱敏不是完美的 DLP；原始日志默认受限访问并按策略保留。

11. 验证引擎与证据质量

11.1 可信谁

可信控制代码与经用户批准的验收定义负责“需要验证什么”；Runner 负责“在哪个环境运行了什么”；Agent 和候选代码均不负责最终评分。测试框架结果也要根据运行位置和可能的干扰级别解释。

v0.1 威胁模型是自己的仓库与可能出错的 Agent，附带基本越界/伪造防护；不承诺在对抗性候选代码面前获得数学意义的可信评价。公共陌生任务托管需要额外威胁模型、VM 隔离和专业安全评估。

11.2 检查结果模型

每条 CheckResult 保存 check_id、required、baseline_expected、candidate_expected、实际 outcome、exit_code、case_count、缺失/跳过 case ID、duration、执行环境摘要、可信级别和 evidence digest。单独的 advisory warning 不改变 must-pass 条件。

必须明确 test_failed 与 verifier_failed：候选 API 返回错误断言可判 fail；用于启动浏览器的镜像损坏是验证基础设施错误；编译候选代码产生语法错误是候选失败。无法自动区分的崩溃先 inconclusive，不为了填满排行榜强行归因。

11.3 校准与失效

每个正式 Task 至少保存基线的预期结果，以及一个经人工确认的正确补丁通过样本；再用一个明显错误或空补丁测试 verifier 是否误报。v0.3 加入更系统的变异/反例校准，但不为所有任务首版强制构建变异测试平台。

有 flaky 证据的任务暂从默认比较集中移出，并记录其失效率。不能仅在某个模型失败时重跑验证，成功时不重跑；验收重试政策在实验前统一固定。

11.4 Review 作为独立层

v0.4 的 ReviewInput 由受控程序组装：任务要求、diff、相关原文件片段、验收摘要和证据引用。隐藏模型/供应商名称，固定 rubric 与上下文预算，标明哪些证据无法完整放入上下文。

仓库内提示、注释和日志作为被审查数据而非 Reviewer 指令。Reviewer 不获得合并、发布或查看凭据的工具。它可以给出缺陷、严重度、位置与理由，也可以返回证据不足；不能任意执行代码或修改硬测试结论。

“实现→Review→一次修复”使用新的 ProtocolVersion，阶段分别计费、分别保存 diff。修复后的 pass 不能回写为 single-pass 的首轮成功。

12. 预算、账号容量与使用量

12.1 区分三种量

第一种是可强制的本地资源限制：并发、运行时间、CPU、内存、进程数量、磁盘。第二种是工具/供应商报告的 token、请求和费用。第三种是订阅余额、服务端隐藏推理和未来计费等不可观测量。

预算字段必须带 enforcement=hard|best_effort|informational。没有供应商原生硬预算能力时，平台不能承诺“达到 5 美元前一定停止”；日志出现额度值时请求可能已发出，停止本地进程也不保证撤回服务端计费。

12.2 UsageRecord

{
  "attempt_id": "attempt-example",
  "source": "cli_reported",
  "source_event_id": "provider-session-7:usage-final",
  "billing_path": "unknown",
  "input_tokens": null,
  "output_tokens": null,
  "cached_input_tokens": null,
  "cost_microusd": null,
  "currency": null,
  "confidence": "unknown",
  "is_cumulative": true
}

缺失为 null，不是 0。若 CLI 只报告某些 token，不补造 total；不同供应商的 cache/reasoning token 口径需保留映射说明。累计快照以其计量 scope 下的最后有效值计算，不能把每次累计事件求和；增量事件以来源 ID 去重。

有精确用量而没有精确价格时，估算另列为 estimated，保存价格来源和日期，不与供应商实际账单覆盖混用。首版可以完全不内置价格表，先保存真实观测和用户手工成本备注。

12.3 调度与额度保护

账号维度默认串行，多个 Profile 共享同一 account_id 时共用容量；不能按模型名拆成三个队列绕过同一账号限制。已知限流时遵守可得的 Retry-After；没有明确时限时使用有上限退避并暂停新试验，用户可恢复。

本平台只控制自己发起的调用，不知道用户同时在 IDE 中使用了多少额度。显示“本平台记录的用量”，不显示“账号全量用量”。不得因为观察不到当前余额而自行创建多个账号或切换计费。

v0.1 对每 Trial 设置 wall-clock 与产物限额；v0.2 增加实验级调用次数/累计观测预算。实际消费尚未结算的运行保持 pending usage，而不是提前按零释放金额预留。金额不确定时只能限制下一次启动，不能追溯保证过去未超额。

12.4 阶段计时

至少分别记录 queue、prepare、agent、collect、verify、cleanup、end_to_end。UI 优先展示 agent 和端到端两个值，其余展开。等待账号、拉镜像或首次构建不能全部算作模型思考时间。

比较速度时记录执行机器、CPU 配额、并发和冷/热缓存。最初可以按随机/交错顺序安排 Profile 以减少时段偏差；无随机对照时用观察性措辞。

13. 统计口径与可比性

13.1 两个必须并列的结果

首 Attempt 可判定通过率：某 Profile 在 eligible Trial 的第一次物理执行中，独立验收为 pass 的数量 / 第一次物理执行能判为 pass 或 fail 的数量。必须同时展示分母、eligible 定义和被排除的缺失原因。

计划交付率：计划内首 Attempt 取得独立 pass 的 Trial 数 / 该 Profile 原计划 Trial 数。排队未开始、取消、认证失败、基础设施失败均仍可见，并按原因分组。实验未完成时不把临时值称最终排名。

第一项更接近在可评判条件下的解题表现；第二项反映完整工具链能交付多少。二者都不是普遍模型能力结论。后续人工重试的最好结果另列为 assisted/retried，不参与首 Attempt 分子。

13.2 任务层聚合

同一个任务多次运行具有共同难度和相关性。v0.3 先对每个任务计算每 Profile 的重复结果，再对任务做等权 macro-average；不能让某个任务因为重复 20 次而压倒只跑 2 次的其他任务。

展示按任务配对的结果：两者都过、只有 A 过、只有 B 过、两者都失败、至少一个未判定。不要在双方可评判任务集合不同的情况下，只比较各自最好看的总体百分比。

13.3 区间、样本量与因果措辞

正式区间优先在任务层进行配对 cluster bootstrap，抽样单位是任务而不是单次 Trial，并保留随机种子、迭代次数和方法版本。数据不足时只显示原始计数与任务分歧。

少于 20 个不同任务时默认提示“探索性样本”，是产品的保守提醒阈值，不是统计定理或充分样本保证。即使任务更多，任务选择偏差、私有仓库特殊性和云端模型变更依旧限制外推。

不把 Wilson/binomial 区间盲目套在相关重复运行上，不输出没有意义的小数点后两位“架构能力”。同一 Agent 对不同模型的比较仍只说明该工具和任务集下的表现。

13.4 成本与质量

成本覆盖完整时，可以计算“所有相关运行总成本 / 验收成功数”，包含失败和约定重试的成本；成功数为 0 时显示 undefined/无成功，不显示 0。费用覆盖不完整时显示 coverage 和缺失原因，不将缺失样本补零。

代码行数、修改文件数、测试数量用于解释工作规模和异常，不作为直接奖励。部分验收项通过可以展示，但不同任务的检查数不同，不能按“通过了多少个测试”跨任务排名。

总体 UI 默认呈现质量、时间、已知成本和人工介入的并列维度，而不是不透明加权总分。自动推荐至少等到数据能解释相似任务表现后再设计，不纳入 v0.3 的承诺。

14. HTTP API、认证与前后端契约

14.1 API 风格

API 以 /api/v1 为前缀，JSON DTO 与数据库模型分开。使用 OpenAPI 作为前后端合同，生成 TypeScript client；不要求首版建设动态 SDK 平台。时刻使用 UTC RFC3339，duration 使用明确单位，字节数为整数，金额使用整数微单位且携带币种。

Pi 启用显式 HTTP status 语义或由 transport 明确编码，不依赖 HTTP method 推断响应码。具体 envelope 由 Lab 冻结并测试，而不是让前端猜测框架默认包装结构。[R5]

14.3 异步提交示例

POST /api/v1/experiments
Idempotency-Key: local-study-001
Content-Type: application/json

{
  "mode": "agent_profile",
  "task_version_ids": ["task-version-registered"],
  "profile_version_ids": ["profile-version-registered"],
  "repetitions": 1,
  "protocol": "single-pass-v1"
}

这些是示例 ID，实际请求必须引用已登记的不可变版本。成功响应建议为：

{
  "data": {"id": "experiment-created", "state": "queued", "trial_count": 1},
  "request_id": "request-created"
}

202 只在计划及 Trial 事务提交后返回。相同主体、操作和 Idempotency-Key 使用相同 payload 时返回原资源；payload 摘要不同返回 409。连接在提交后断开时，客户端可以使用同 key 恢复，不新增付费运行。

14.4 错误分类

400 为格式错误，401 未认证，403 未授权，404 资源不存在或按策略隐藏，409 状态/版本/幂等冲突，422 配置不可执行，429 本平台容量/请求频率限制，503 无法安全持久化或正在停止。

Provider 的限流是运行域事件，不应机械映射为最初 POST 的 HTTP 500。对客户端返回稳定的 error.code、公开 message、可公开 details 和 request_id；凭据、原始命令环境和内部 SQL 不进入响应。

14.5 本机也需要认证

loopback 不等于没有浏览器跨站风险。首次启动使用一次性初始化流程创建管理员；后续采用受保护会话或本地 API token。Cookie 使用 HttpOnly、SameSite，远程 HTTPS 才设置符合部署的 Secure 策略；写请求有 CSRF 防护。

校验 Host/Origin，默认关闭 CORS，限制可信代理，防止恶意网页通过本机 API 启动命令。不可把长期 token 放 URL 查询参数。SSE 使用同源会话，不通过可泄露的查询字符串携带密钥。

登录后仍进行资源级授权。Pi 身份只能从已校验的登录态映射，不能从请求 user_id 建立 Principal；服务方法保持明确授权边界。[R5] 即使首版单用户，也要测试未登录不能执行和读日志。

15. 前端设计与实现约束

采用 React、TypeScript、Vite 与一个统一组件体系；路由、服务端状态缓存和表格组件选择团队熟悉的稳定组合并锁版本，不在本文指定“最新版”。这是本项目的工程选择，不是声称某套 UI 栈性能最强。

页面按产品文档第 9 章实现。前端不重算权威 Verdict，不根据日志关键词切换为成功；汇总由后端返回明确口径，客户端只做展示和交互。

长日志列表虚拟滚动，按页加载历史；Diff 支持文件级分段和二进制占位；超大文件只显示摘要并提供受限下载。编辑器只用于任务/配置草稿和只读 diff，首版不提供能修改运行中工作区的完整 IDE。

创建实验表单先调用本地计算/后端预览，明确 Trial 展开数与权限；真正执行仍以一次事务的 POST 为准，不能在每切换一个模型选项时提前启动。

界面上固定展示四种结果状态，不单靠颜色表达。空数据、权限失败、来源未知、日志截断、配额阻塞、清理隔离和模型解析不一致都有明确文案。Fixture 不包含假装真实的模型分数；演示数据统一标注 demo。

17. 运维、备份、保留与观测

控制日志与 Agent 日志分开。控制日志记录 request_id、experiment/trial/attempt、阶段和错误类型，默认不打印 prompt、源码、完整 env 或凭据。指标按类型聚合，避免把每个 run ID 作为高基数 metric label。

优先指标：queued/active/quarantined 数、账号阻塞、准备/执行/验证耗时、取消到 clean 耗时、丢失/截断事件、SQLite busy、制品增长和未知 usage 比例。不要把业务日志全部送入外部服务，默认保持本地。

备份使用经验证的 SQLite 一致性快照流程；不能在 WAL 模式下随意只复制主数据库文件。v0.1 可采用维护模式：停止新调度，结束或确认活跃任务，关闭/一致性导出数据库，再按引用清单备份不可变制品。更平滑的在线备份后续增加，须实测驱动能力。[W8]

升级前备份，迁移在单实例锁下进行。首版不承诺任意 down migration；不兼容时保留旧程序与备份以回退。Profile 依赖的 CLI 版本与系统升级分开，禁止服务升级顺手执行所有工具的自动更新。

保留策略按原始日志、规范事件、工作区、改动包和报告分别管理。默认清理临时工作区，不自动删除被报告引用的核心补丁和检查摘要。磁盘水位超过阈值先阻止新任务，再按明确规则清理未引用临时文件；未知 orphan 先隔离，不能全盘 rm -rf。

18.3 开工前必须验证但不阻断文档的事项

第一，Pi 当前固定提交在拟用 Go 工具链上的构建与测试，宿主 HTTPHandler/资源关闭/SSE 的实际行为。第二，用户实际安装的三个 CLI 版本、登录模式和 DeepSeek 的真实 provider/model。第三，Intel Mac/Docker 与 Linux 执行环境的认证和取消兼容性。第四，SQLite driver 的 PRAGMA、备份与断电行为。第五，模型端实际可观测 usage 与预算支持。

这些不确定性有明确的 v0.0 实验，不要求先把整个框架升级重写。失败就缩小已认证兼容矩阵，而不是编造“全部已支持”。

18.4 为什么不直接包一层 Harbor 就结束

Harbor 已有任务结构和独立验证能力，值得后续互操作；但本项目第一目标是你的实际 CLI/账号接入、个人项目流程、预算可观测性、差异审查和本地使用体验，不是单纯运行某个公开榜单。[W10][W12]

因此只自建必须的个人闭环，不自建大型通用 benchmark 集群。首版保留 task/prompt/environment/verifier/artifact 概念的映射空间；v0.5 可作为外部 executor 导入 Harbor 结果或任务子集。格式兼容必须报告未映射字段与不同隔离假设，不能仅修改文件名就声称兼容。

20. 开发交付检查清单

评审时先检查：任务与验收是否冻结；执行是否在独立环境；是否真能清理所有子进程；失联是否会重复调用；unknown 是否被错误变成零；Agent 文本是否被当成可信控制事件；统计是否把重试成功当首次成功。

然后检查：Pi 依赖是否仅在边界；SQL 与文件所有权是否唯一；API 与前端是否共享合同；CLI 版本是否锁定；隐藏验证是否意外暴露；非认证平台是否被标成支持；模型能力结论是否有对应任务和证据。

最后才检查：页面细节、图表种类、适配器数量、自动化程度和后续路由。第一版正确地解释十次真实运行，比不可信地展示一万次漂亮分数更有价值。

Coding Agent Lab · 实施任务包

用途：把产品与技术设计拆成能够单独 Review 的工单。
基线：2026-10-04。先读 产品需求文档 第 1、3、12 章，再读 技术设计文档 第 2—7 章。本文不是要一次完成所有版本。

1. 执行规则

先确定契约与负例，再写实现。一个工单只有一个负责人；同一时刻不要让多个 Agent 随意修改 schema、状态机、公共 DTO 或数据库迁移。并行适合发生在边界固定之后，如独立适配器、页面、已确定契约的测试。

工程判断不能由模型修改测试口径来绕过。出现文档冲突时记录 ADR/问题，不自行放宽安全限制，也不为了通过 CI 删除检查。实现者可以补测试，但不能单方面更改已批准的验收预期。

建议主控负责跨模块 Review 和合并，执行 Agent 负责有限改动；独立 Reviewer 检查事实与负例。这里没有根据特定模型名称预设能力排行，分工应按实际结果调整。

2. v0.0：先验证四个真实前提

工单 产物 验收
B00 · Pi 版本验证 固定依赖版本、最小服务、构建记录 当前提交可构建；HTTPHandler、资源 Start/Stop、SSE 不依赖虚构 API
B01 · 存储验证 SQLite 临时库、迁移与事务测试 PRAGMA 每连接生效；短事务/CAS；关闭后能恢复已确认状态
B02 · 账号与 CLI 验证 doctor 报告、脱敏真实事件 fixture 用户授权的小任务确实改文件；知道走哪条授权/计费路径；模型 ID 可用
B03 · 执行环境验证 假 CLI、取消与清理测试 子进程会派生孙进程；取消/父进程崩溃均可清理或明确 quarantine

B02 只选择当前最容易合法跑通的一个入口，不强制先 Cursor。没有用户允许时只做静态探测，不使用真实模型调用来试错。

3. v0.1：单次可信闭环

M01 · 领域契约与状态机

范围：internal/domain、契约测试、必要 ADR。定义 TaskVersion、ProfileVersion、Experiment、Trial、Attempt、Verdict、CleanupState；实现纯函数状态转换与比较指纹。

必须测试非法转换、取消与终结竞争、旧 Attempt 回报、已发布版本不可变。暂不写数据库和 CLI。完成后将字段冻结为 DTO/schema，后续 Agent 不随意改名。

M02 · SQLite Store 与幂等提交

依赖 M01。实现 schema/migrations、Task/Profile 版本保存、单 Trial Experiment、幂等提交和容量占用事务。只支持 SQLite，不预先做多数据库抽象工厂。

必须测试相同请求重复提交只出现一组 Trial、同 key 不同 body 冲突、终态和取消的 CAS、失败事务无半个计划。写数据库的唯一进程是控制面。

M03 · Runner 协议与假 Agent

依赖 M01。实现同一可执行文件的 Runner 子命令、受限私有 IPC、按 Attempt 的事件序号和能力凭证、stdout/stderr 独立捕获、超时和取消。

假 Agent 应可模拟成功、失败、挂起、派生子进程、重复终结、超大输出、伪造平台事件。不得让假 Agent 的 {"type":"Finished"} 直接控制任务状态。使用假 Agent 完成恢复测试后再接真实账号。

M04 · 独立工作区与改动包

实现授权源的固定基线、独立副本、文件清单、收集/应用改动包与 diff 导出。首版明确处理普通文件、二进制和删除，拒绝不支持的 symlink/submodule，而不是留下不确定行为。

必须测试未跟踪新文件、修改 .git/index、路径穿越、超大文件、隐藏材料和源仓库不被修改。输出摘要应在干净基线重建后可再次验证。

M05 · 一种执行环境 + 一种真实 Adapter

依赖 B02/B03/M03/M04。优先认证 Docker 路径，只接一个真实 CLI。建立净化的环境、明确的认证引用、固定版本 argv、事件解析与实际模型记录。

未经用户批准不使用自动放开权限的参数。尚不支持的网络限制写成不支持，不能只加一个 enum 就显示“已沙箱化”。出现输出解析变化保留原始记录，不默认成功。

M06 · Verifier 与任务校准

依赖 M04/M05。实现基线预检、独立候选环境、build/regression/acceptance/policy 检查、数量/ID 约束和证据文件。先用两个维护过的示范任务证明正确补丁通过、错误/空补丁失败。

测试脚本异常与候选测试失败分开；隐藏材料仅在验证端出现；记录 inprocess/blackbox 可信度。不能以 Agent stdout 的测试摘要为权威结果。

M07 · 生命周期整合和恢复

依赖 M02—M06。将固定 scheduler/supervisor 循环接入 Pi；启动/关闭职责唯一；单 Trial 默认无自动重跑。实现 journal 恢复、身份核对、quarantine 和账号容量释放条件。

重点测试：取消返回 202 后并非立即 clean；旧 fence 不覆盖新结果；控制面重启不重复发起付费任务；单次模型失败不关闭整个 Pi 应用。

M08 · API、安全和实时数据

在 M01 契约基础上实现技术文档第 14 章的首版 API 子集，加入登录、资源授权、Host/Origin/CSRF、幂等请求、分页、SSE 重放和错误映射。

允许并行于部分 Runner 开发，但只能使用固定 DTO 和假数据 fixture。不要先把“任意 shell 命令执行接口”暴露出来再补认证。

M09 · 最小 Web 交互

依赖 M08 契约。只做 Setup/配置检查、项目任务、单次提交、运行详情、差异/检查/日志与导出入口。不做排行榜、无限画布、终端 IDE 或模型聊天窗口。

页面展示真实 execution/verdict/cleanup 三组状态。unknown 金额显示未知；无结果显示空状态，不填演示分数。演示截图必须带 demo 标记。

M10 · 使用量、制品与发布回归

补齐 nullable usage、累计去重、时间分解、日志上限、制品 manifest、维护模式备份与导出。运行技术文档的 v0.1 测试集，生成平台/CLI/认证模式兼容矩阵。

交付条件不是“单元测试全绿”，而是有一次真实 CLI 的执行—独立验收—取消/恢复—导出完整记录。用量不可得可以发布，但必须显示未知；清理不可控或误报 pass 不可发布。

4. v0.2：可并行但不同时改核心协议

在 v0.1 稳定后，可并行安排三个工作包：补齐剩余两个适配器；实现有界全局并发与账号容量；实现矩阵与基础对比页面。适配器共享固定 contract，但各自拥有真实脱敏 fixture。

矩阵展开、容量、重试和 usage 的集成最终由主控统一 Review。至少用两个真实项目检查结果可解释性；缺少数据不生成模型强弱结论。

5. v0.3 以后的工单

v0.3：受控模型模式、可比性判定、重复实验、按任务配对/聚合、统计方法版本化、flaky 校准。

v0.4：人工 Review、可选盲评、一次修复的独立 protocol。先能解释单阶段结果，再做多阶段。

v0.5：Harbor 子集、外部签名触发/通知。ACP/ATIF/Herdr 分别立项，不与产品核心捆绑同时交付。
